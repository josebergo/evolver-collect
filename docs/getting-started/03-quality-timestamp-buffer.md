# 数据质量、时间戳与断点续传

这三个概念决定了"数据可不可信"，是数采和普通"读一下"的本质区别。

## 数据质量（Quality）

每个数据点都带质量戳：

| 质量 | 含义 | 什么时候出现 |
|---|---|---|
| `Good` | 可信 | 正常读到 |
| `Uncertain` | 存疑 | 协议定义的中间态（如 OPC UA 的某类状态码） |
| `Bad` | 不可信 | 断线、超时、地址非法、CRC 错 |

**关键设计**：本系统在设备断链时会把该通道全部点位以 `Bad` 通告一次，然后由重连机制恢复。下游系统看到 `Bad` 就知道这段时间的数据不能用——而不是永远收不到数据、分不清"没变化"和"断了"。

## 时间戳

- 默认 **采集侧时间戳**：网关读到数据的那一刻（毫秒级）
- 网关和设备之间通信有延迟，所以更严谨的做法是设备侧时间戳（v1.x 计划支持透传）
- 现场务必给网关配 NTP 对时，否则跨网关数据无法对齐

## 断点续传（本项目的招牌能力）

场景：车间网络抖了 10 分钟，这 10 分钟的数据丢不丢？

```
正常：采集 → 内存队列 → MQTT/Kafka/HTTP → 成功 ✔
断网：采集 → 内存队列 → 发送失败 → 写入本地 SQLite 离线队列
恢复：重连成功 → 按顺序回放积压 → 发送成功 → 推进水位删除 ✔
```

- 离线队列容量可配（默认 100 万点/北向，FIFO 淘汰防写满磁盘）
- 北向状态页能实时看到"积压条数"，恢复后自动清零
- 报文格式与实时数据完全一致，下游无需区分回放和实时

## 心跳与死区

- **死区（Deadband）**：值变化小于阈值就不上报，防止抖动刷屏。开关量只在上报变化时发布。
- **首值必发**：启动后每个点位至少发布一次，让下游知道"这个点存在且当前是这个值"。
